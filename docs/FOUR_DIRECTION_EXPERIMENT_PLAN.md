## 1. 固定前提與要回答的問題

- **收到的 Cell ID 是該次量測的最新值**，依使用者確認的機制條件評估，不再以未驗證的 CNI 過時作限制。
- 每次成功 probe 至多一個 cell；可累積歷史。探測間隔內可能漏掉中間 cell，並不知道真正切換的瞬間。
- 本輪將 fresh INVITE 間隔設定為 10 秒；實際間隔可能更長。2026-10-27 程式核對確認 10 秒是本實驗選定值，並非目前 UI／native 的硬性下限。採集保留現行清理、取消與重啟規則。
- 推論只用主叫端取得的 cell 與觀察時間；未來若加入其他實際可見欄位，必須另列比較。目標端感測資料只供校準、真值與控制。
- 普通場域 Wi-Fi 是觀察條件。失去 CNI 保留為未知；移動熱點屬不同應用條件，不作本方案的默認補救。
- 已知場域調查可接受。跨日期、未採過的點、未去過的建築物，是三種不同的泛化問題。

**共同研究問題：** 在相同探測成本與可輸出比例下，多筆最新 Cell ID 的集合、比例、順序和動線，能否提供單筆 ID 沒有的區域／樓層／邊界資訊？若可以，能否保留事件辨識品質並少查詢？

## 4. 第一輪：先用 60～90 分鐘選場與篩選

選一個可重複進出的已知場域，優先有兩個以上樓層、水平走廊、樓梯，以及至少部分出入口兩側都能使用普通 Wi-Fi。三樓、電梯、第二入口是有條件增加的項目。

1. 在簡單平面圖上標 **6～8 個已知點**：兩層各兩個水平位置、入口內、入口外；可行時加鄰棟／另一側外部負例。跨樓的兩點盡量位於相近水平位置。
2. 各點停留約 **3 分鐘**；以目前允許的密集頻率採集，使用實際發送時間。不要將不同點按固定樓層順序全部走完，避免地點與時間／抵達路線完全重合。
3. 做水平走動、上／下樓、跨入口、門口折返、同點停留；各類先至少兩次。在代表位置加入約 10 分鐘原地控制。
4. 記錄哪些路段有 CNI、哪些失去 Wi-Fi；即使沒有 CNI，也記錄真實動作和所有 attempts。這輪用於選擇測試點和方法，不當作獨立驗證集。

**第一輪要得到的結論：** 哪些邊界會伴隨可觀察的 ID／序列變化？哪些樓層／區域共用相同模式？原地變化是否複製了候選地標？若換樓完全沒有可重現差異，就先不擴大該場域的精確樓層分類。

若邊界兩側無法保持普通 Wi-Fi，將它保留為端到端可用性實驗；另找仍可觀察的區內邊界測辨識機制。兩者分開報告，不能用移動熱點掩蓋原有條件。

### 每個方向的比較與失敗判準

| 方向 | 必做比較／評分 | 何時停止或縮小主張 |
|---|---|---|
| **1 建築物／區域** | 多數類別、單筆 ID、30／60／120 秒集合／分布、序列；混淆矩陣、外部誤判為內部、候選區域大小、未知比例。 | 候選「專屬」ID 在鄰棟／室外常見；歷史不優於單筆，或差異只隨抵達路線／日期而變。 |
| **2 樓層／垂直區域** | 同樓不同水平位置 vs 同水平不同樓；冷啟動 vs 已知入口；原始 ID vs 合理分組；圖＋時間基準 vs 圖＋ID。報精確樓層、樓層群、換樓通知延遲。 | 真實換樓與水平移動的歷史無法區分；收益完全來自已知起點／固定路線。可另測事前定義的粗樓層群，不事後改類別。 |
| **3 Cell 切換地標** | B 單獨 vs A→B vs 短序列；報候選路段長度與真值保留率、原地誤觸發、通知延遲，按方向／速度分層。 | 保留同等真值時範圍沒有縮小，或原地／替代路徑常產生相同地標。 |
| **8 離開與少 probe** | 確認事件／全部實際離開，30／60／120 秒內偵測比例，誤報／內部小時，短暫離開漏報、未知時間、全部嘗試數。 | 大部分離開只留下與原地斷 Wi-Fi 相同的缺資料；或較少查詢沒有勝過相同品質的固定頻率。 |

地標位置要保留「前一筆 A 到第一筆 B 之間」的位置／時間區間。室內用路徑已知點與通過時間界定，不把中點當成真實 handover，也不因室內 GPS 漂移而宣稱數公尺精度。

**事件計分：** 每個確認警報與同區域的一個尚未配對 EXIT 一對一配對，須在該次 EXIT 後、下一次 ENTER 前；同一次離開的重複警報不增加成功數。提早的「確認離開」算誤報，風險預測另計。未知、失聯與未偵測的實際離開全部保留在事件分母，時間不確定則另標區間。未在外維持完整評估窗的事件另列短暫離開，不混入持續離開的 120 秒指標。

## 6. 第三輪：誠實測少 probe

先有可用的區域／離開辨識，才比較排程。**停留時少查詢仍需定期檢查；完全不 probe 且沒有另一個觀察管道時，無法即時得知已離開。**

1. 固定 10／30／60 秒為比較組；實際受支援最小間隔與流程約束。動態組可先用 10～60 秒有上限排程；這些是測試設定，不是結果。
2. 先在密集紀錄上做因果重播：策略只看自己先前選到、且**結果當時已實際可用**的 attempts，再決定下次查詢。ID 在 CNI 回應到達後才釋出，沒有 CNI 的結果在原有流程結束／timeout 後才釋出；不能在送出時預先看結果。未選到的中間 ID 只能供事後評分，特徵從策略已看過的資料重算。
3. 以原始 attempts 為機會集合，採「選擇下一個不早於排程時間、且已滿足最小間隔的紀錄」的映射，事先固定，不看該筆是否成功才挑選。下次發送不得早於決策當下、上一筆實際發送＋10 秒及原有流程允許發送的時間；每次按映射後的實際時間繼續排程，不追趕理想時鐘。此法只近似固定 30／60 秒，不冒充精確採樣。排程最大間隔也不保證故障／失聯時的實際觀察間隔。
4. 同時改變偵測門檻與查詢策略時，要在訓練資料上等量調整並凍結；先比較共用偵測器，避免將較寬鬆的規則誤當排程改善。
5. 重播假設 probe 頻率不影響後續可觀察性，因此只是候選篩選。若有收益，再以前瞻實際排程，在另一日期反覆走相同類型路線，交錯／平衡固定與動態組。
6. 畫「每小時嘗試次數—事件漏報—實際通知延遲—未知比例」的取捨。與**能達相同事件品質的固定組**比成本；單純比最密集組少查，不足以支持排程貢獻。

短暫離開再返回獨立計分，不能只看最後狀態又相同。若需要提前提醒，可另評「接下來 60 秒離開風險」及其提前時間／精確率；這不算已確認離開。

## 7. 實際要保存的資料

| 必需資料 | 現有來源／要注意的事情 |

| 每一次 attempt 結果與缺口 | 有 CNI、回應但沒有 CNI、沒有回應、取消／失敗、process restart；失敗嘗試也計成本。重送不當新 probe。 |

Cell ID 當類別，數字差沒有距離或樓層意義。主叫端的 Wi-Fi 狀態也不是目標端 Wi-Fi；各自來源需標明。

### B. 真值與校準：LocationData＋場域標註

- **已知場所：** `site_id`、`building_id`、`floor_id`、`zone_id`、`point_id`，含樓層牌／門／地標對應的簡圖與入口、樓梯、電梯連通關係。地理邊界在採集前定義。
- **時間事件：** 到點／離點、進入／離開指定區域、換樓起訖、過已知路徑點、停下、折返、Wi-Fi off/on。記錄時間與人工標記誤差；室內以已知點／樓層為真值，GPS 只輔助。
- **連續紀錄：** 保留 LocationData 原始位置／fix age／精度／速度，註冊 cell 的 `registered`、測量時間／age，鄰居與訊號、Wi-Fi 與電源欄位；缺值保持缺值。這些欄位不偷偷輸入 caller 模型。
- **實驗條件：** 實際日期、路線、方向、步速指示、手機持法／朝向、業者／機型、普通 Wi-Fi 或其他網路、螢幕／記錄設定、哪一趟／哪一次到訪。
- **對時：** 沿用自動時間與離線配對，記錄已知鐘差或人工事件不確定範圍；無法確定時用區間，不宣稱秒以下事件精度。不同手機的單調時鐘不直接相減。

### 現有事件文字格式（少量錨點／抽查用）

LocationData 已支援任意文字 label，可使用下列約定；不要求增加新匯出欄位，也不要求每次行動都輸入。開始／結束一段已知樓層可用簡短 `F1_START`／`F1_END`，中間樣本離線自動繼承；下列較完整文字保留給需要的地點錨點與對照。

```text
AT_POINT|site=A|floor=F1|zone=west|point=P01|visit=V01
LEAVE_POINT|point=P01|visit=V01
ENTER|site=A|zone=inside|door=D1|episode=X01
EXIT|site=A|zone=inside|door=D1|episode=X01
VERTICAL_START|from=F1|to=F2|via=stairs|trip=T01
VERTICAL_END|floor=F2|via=stairs|trip=T01
CHECKPOINT|point=CP02|trip=T01
TURN_BACK|point=CP02|episode=X02
STOP|point=CP02|trip=T01
RESUME|point=CP02|trip=T01
WIFI_OFF|stationary=true|episode=W01
WIFI_ON|stationary=true|episode=W01
```

`WIFI_OFF` 等目標標記只供評分。若首輪不便準時按 App，可用有時間的觀察紀錄側檔，保留標記誤差，不事後依 Cell ID 變化反推事件時間。

### C. 減少人工：自動候選＋區段標籤＋少量核對

**樓層／過門真值是目標端的實驗參考，主叫端推論仍只用允許的 CNI 資料。** 自動估計標籤與經獨立核對的標籤要分級；不把另一個未驗證的分類器當成無誤真值。

#### C1. 樓層：高度可以協助，但現有 fused altitude 要先驗證

2026-10-27 重讀九份真值匯出：2,185 筆皆有 `altitudeM`、`verticalAccuracyM`，provider 皆為 `fused`；垂直不確定度中位數 **2.810 m**、P90 **3.391 m**。這是系統回報的不確定度，未量到實際高度誤差；既有資料也沒有已核對的換樓標籤。

Android 的 altitude 以 WGS84 橢球為基準；verticalAccuracy 是 **68%** 的估計範圍，不能當硬誤差上限。若兩層中心相距 3 m，最近樓層的分界距中心僅 1.5 m；目前不能直接把高度除以樓高後取整數當樓層真值。相對高度仍可能有用，須用已知樓層檢查穩定偏差／漂移與可分辨性。[Android Location 官方定義](https://developer.android.com/reference/android/location/Location#getVerticalAccuracyMeters())

| 方案 | 人工負擔 | 實際條件與用途 |
|---|---|---|
| **整段樓層標籤，先用現有功能** | 進入／離開該樓層實驗區段各記一次；中間不需操作。 | 在同樓停留或水平走動時，自動套用整段樓層。未知的樓梯／電梯過程保留轉換區間；區域／地標任務仍需少量空間錨點。 |
| **現有高度離線分段** | 少量已知樓層起訖／抽查。 | 先做一次上樓再返回測試，檢查同樓不同位置與跨樓高度區間。只有通過核對的穩定區段才標樓層，重疊／轉換／缺 fix 為未知。資料平滑不保證消除固定偏差。 |
| **相對氣壓高度追蹤** | 一次場域樓層對應校準；每場開始確認樓層並重設壓力參考，結束／少量中途核對。 | 須先實機確認氣壓計並新增紀錄。採各層相對壓力／高度區間，處理漂移與樓高不同；不假設一次校準永久有效。 |

目前 LocationData 沒有 `TYPE_PRESSURE`／氣壓紀錄程式，目標手機是否能提供該感測器仍待實機確認。不能由 `altitudeM` 有值推論它來自氣壓計。[Android 環境感測器文件](https://developer.android.com/develop/sensors-and-location/sensors/sensors_environment)

[FloorPair（2019）原文 §4](https://pmc.ncbi.nlm.nih.gov/articles/PMC6720727/)提供相對氣壓地圖、入口樓層與參考壓力初始化的方法；它需要樓層對應與更新參考，不能把最佳實驗結果當成我們自動標籤的保證。氣壓只供實驗標籤，不加入 caller 模型。

**室內與樓高的物理意義：** 低海拔近似每升高 1 m，氣壓下降約 0.12 hPa；假設相鄰樓層差 3～5 m，約差 0.36～0.60 hPa。FloorPair 也在 COEX 與現代百貨 COEX 分店作過實驗，因此室內／百貨公司的尺度本身不會消除高度壓差。小幅變化能否在本手機穩定分辨，仍需量測；室內加壓、空調與漂移可疊加影響，不能將任意壓力變化直接當換樓。[FloorPair §2、§5.2](https://pmc.ncbi.nlm.nih.gov/articles/PMC6720727/)、[HotMobile 2014 原文](https://hotmobile.org/2014/papers/hotmobile_final/hotmobile2014-final37.pdf)

**低操作替代：** 可規劃「選樓層／點位→開始固定三分鐘區段→提示結束後才離開」的一鍵定時模式，一次標記涵蓋整段資料；移動段不自動沿用上一樓層。這需要遵守停留時間、記錄偏離流程的情況，且目前尚未實作。現有 App 可先用簡短起止標記達到相同的區段標籤效果。

#### C2. 進出：按需要的邊界尺度選真值方式

| 方案 | 能自動產生什麼 | 仍需的核對／限制 |
|---|---|---|
| **位置／地理範圍** | 大區域的明確內部、明確外部區段與進出候選。 | 建築邊緣保留未知帶；定位精度是估計而非硬界。系統 geofence 的通知時間不等於實際過門時間，不能直接用它評秒級延遲。 |
| **目標端 Wi-Fi／BSSID／RSSI** | 連線、漫遊與環境改變候選；可自動圈出需核對片段。 | 斷線不等於離開：原地關 Wi-Fi、漫遊、室外仍連線都要保留。現有 BSSID hash 含 session salt，跨 session 的字串不可直接當同一 AP。 |
| **明確內／外位置夾出的區間** | 自動找最後明確在內、第一筆明確在外的參考，保留離開時間區間。 | 前提是位置精度與獨立確認足夠；邊界區間太寬時，只評內外狀態，不宣稱精確過門延遲。 |
| **現有手機的簡短過門確認** | 過門留一次時間確認，不要求輸入長事件文字。 | 現有 App 用簡短 `IN`／`OUT`；可再規劃依已知起始狀態切換的一鍵模式。記錄按鍵反應時間的不確定性，不能假定零延遲。 |

Android 官方 geofencing 建議約 **100～150 m** 半徑，背景通知平均可能約 **2～3 分鐘**，因此只適合較粗候選，不當單棟入口的秒級真值。[官方文件](https://developer.android.com/develop/sensors-and-location/location/geofencing)

**百貨公司的預設選擇：** 先以現有位置／Wi-Fi 自動找候選；較粗區域用已確認的內外停留段評分。若要評精確門線／通知延遲，現階段每次真正過門保留一次簡短確認，避免把未驗證的自動候選當真值。之後可依手機自動標記的實測品質再減少人工；不採錄影或現場設備，也不把 Wi-Fi 覆蓋邊界當成實體門線。

#### C3. 標籤品質與最低人工流程

1. 全部感測與 attempts 自動連續記錄。少量確認記錄標明來源；未核對的高度／Wi-Fi／geofence 輸出保留為候選，不直接計為確認真值。
2. 樓層先採區段標籤；開始／結束與少量抽查足夠覆蓋大量固定樓層樣本。有條件實作定時區段後，每段開始確認一次，結束自動切回未知；真正換樓段只有在獨立高度／氣壓量測通過核對後才自動縮小範圍。
3. 過門候選由位置／Wi-Fi 提出；精確事件先保留實體過門確認，也抽查一部分沒有觸發的時段，避免只看成功候選而漏掉事件。不具可靠參考的候選不算已確認過門。
4. 離線側檔保留 `labelSource`、`confirmed/estimated/unknown`、錨點與事件最早／最晚時間；候選標籤與確認子集分開報告，自動標記覆蓋率／錯標也要報。
5. 真值可用事後獨立感測與少量確認整理，但這些資料與未來事件不能輸入 caller 即時策略。不能用 serving cell 或 CNI 是否出現產生 EXIT 標籤後，再宣稱同一訊號辨識離開成功。

本更新是降低標記成本的設計，尚未新增氣壓、一鍵定時區段或自動標籤程式；不將未實作功能列為已有資料。錄影與現場部署已移出本百貨公司方案。

## 8. 防止看似成功的評估方式

- 以完整到訪／路線／日期切分，不能隨機拆相鄰或重疊時間窗。第一天建模型，第二天凍結測試；至少另留水平點或抵達路線檢查場域內泛化，點／路線需事先指定。
- 即時模型只看截至決策當下的歷史；已完成整趟路線的回溯重建另列，不算當時已定位。未知初始位置與已知入口模式分開。
- 同一探測預算、觀察時間窗與可輸出比例比較；同時報正確率、未知率、啟動等待時間。固定停留和切換期間分開，不能讓大量原地樣本掩蓋換樓／離開失敗。
- 兩天與少數 episode 只是初篩。數百個 probe 不等於數百次獨立進出；以 episode／到訪為重複單位。第二場域、更多日期與裝置是成功後的複核需求。
- 可用 target ID／RSS 做額外診斷基準，檢查該場域是否存在更豐富的無線差異；必須明標為 target-assisted，不算主叫端方法成果。

## 9. 建議執行順序與交付

**先做第一輪場域篩選；有可重複差異後，收第二輪共用資料；最後才測實際省 probe 排程。**

第一輪應交付：標註平面圖、資料配對清單、各點 ID／缺資料摘要、候選切換區間、哪些方向繼續／改成粗區域／暫停的理由。第二輪應交付四方向的獨立測試報告；第三輪應交付成本與事件品質的取捨，連同未偵測與未知事件。

目前最值得先驗證的是「**已知場域的 ID 歷史是否提供可重現的位置資訊**」。若成立，四個方向能互相支援；若不成立，結果應限定到該場域／條件，避免立即改用更複雜的 AI 或宣稱所有場域都不可行。
